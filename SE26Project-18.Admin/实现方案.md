# 管理员后台 — 最小管理闭环 实现方案

## 任务目标

为现有的搭子匹配工具实现一个极简的管理员后台 Web 页面，仅提供最基础的管理闭环功能：登录 → 查看待处理事项 → 处理 → 提交结果。不需要仪表盘、数据统计、图表等冗余功能。


## 一、背景信息

### 现有系统架构
- **前端（用户端）**：React Native + Expo
- **后端**：.NET Core（ASP.NET Core Web API）
- **数据库**：MySQL

### 新增需求
- 管理员使用独立表（Admins），不与 Users 表混合
- 管理员从 Web 端登录，走独立入口
- 仅实现一个管理闭环，不做完整后台系统


## 二、现有代码分析 & 需要改动的地方

### 2.1 Report 实体（需改造）

当前 `Report` 实体**没有** `Status` 和 `HandledAt` 字段，无法区分"待处理/已处理/驳回"。

```csharp
// 当前：只有基本字段
public class Report {
    long Id, ReporterId, TargetId;
    User Reporter;
    ReportTargetType TargetType;
    ViolationType ViolationType;
    string Content;
    DateTime CreatedAt;
}

// 需要新增：
public ReportStatus Status { get; set; } = ReportStatus.Pending;  // 新增枚举
public DateTime? HandledAt { get; set; }                           // 处理时间
public long? HandledByAdminId { get; set; }                        // 处理的管理员
```

需要新建枚举 `ReportStatus`：`Pending`（待处理）、`Resolved`（已处理）、`Rejected`（驳回）

### 2.2 Feedback 实体（需改造）

当前 `Feedback` 实体**没有** `Status` 和 `HandledAt` 字段。

```csharp
// 需要新增：
public FeedbackStatus Status { get; set; } = FeedbackStatus.Pending;  // 新增枚举
public DateTime? HandledAt { get; set; }
public long? HandledByAdminId { get; set; }
```

需要新建枚举 `FeedbackStatus`：`Pending`（待处理）、`Resolved`（已处理）

### 2.3 User 实体（无需改动）

`User.Status` 已支持 `Normal` / `Banned` / `Deleted`，`UserService.UpdateUserAsync` 已支持更新 `nickname` / `avatar` / `signature`。

**需要扩展**：`UpdateUserAsync` 增加 `status` 字段支持，允许管理员修改用户状态。

### 2.4 Recruitment 实体（无需改动）

`Recruitment.Status` 已支持 `Open` / `Closed` / `Deleted`，`RecruitmentService.UpdateRecruitmentAsync` 已支持更新 `status`。

### 2.5 Game 实体（无需改动）

`GameService.UpdateGameAsync` 已支持更新游戏信息。

### 2.6 新增 Admins 实体

```csharp
[Table("admins")]
public class Admin {
    public long Id { get; private set; }
    public string Username { get; set; }
    public string PasswordHash { get; set; }       // BCrypt
    public DateTime? LastLoginAt { get; set; }
    public DateTime CreatedAt { get; private set; }
}
```

## 四、API 设计

所有管理 API 统一走 `/api/admin` 前缀，需要 Admin JWT 认证。

### 4.1 认证

```
POST /api/admin/login
Body: { username, password }
Response: { access_token, admin: { id, username } }
```

### 4.2 举报管理

```
GET    /api/admin/reports?status=pending              → 举报列表（可按状态筛选）
PUT    /api/admin/reports/{id}                        → 处理举报
       Body: { status: "resolved" | "rejected" }
```

### 4.3 反馈管理

```
GET    /api/admin/feedbacks?status=pending             → 反馈列表
PUT    /api/admin/feedbacks/{id}                       → 标记已处理
       Body: { status: "resolved" }
```

### 4.4 用户管理

```
GET    /api/admin/users?search=xxx                     → 搜索用户
PUT    /api/admin/users/{id}/status                    → 修改状态
       Body: { status: "封禁" | "正常" }
PUT    /api/admin/users/{id}/clear                     → 清空个人信息
```

### 4.5 招募管理

```
GET    /api/admin/recruitments?search=xxx              → 搜索招募
PUT    /api/admin/recruitments/{id}/status             → 关闭招募
       Body: { status: "已关闭" }
```

### 4.6 游戏管理

```
GET    /api/admin/games?search=xxx                     → 搜索游戏
PUT    /api/admin/games/{id}                           → 修改游戏信息
       Body: { name, cover, icon, description, company }
```


## 五、管理闭环

```
管理员登录 → /admin/login
    │
    ▼
管理主页 → /admin（卡片入口，显示待处理数量）
    │
    ├── 举报列表 → /admin/reports
    │   └── 点击"已处理"或"驳回" → 状态更新 → 闭环
    │
    ├── 反馈列表 → /admin/feedbacks
    │   └── 点击"标记已处理" → 状态更新 → 闭环
    │
    ├── 用户管理 → /admin/users
    │   └── 搜索用户 → 封禁/解禁/清空信息 → 状态更新 → 闭环
    │
    ├── 招募管理 → /admin/recruitments
    │   └── 搜索招募 → 关闭招募 → 状态更新 → 闭环
    │
    └── 游戏管理 → /admin/games
        └── 搜索游戏 → 修改信息 → 保存 → 闭环
```

## 九、关键注意事项

1. **Admin 认证独立于 User**：Admin JWT 的 Role Claim 设为 `"Admin"`，与普通用户的 `"User"` 区分
2. **Report/Feedback 不删除**：只改状态，保留数据
3. **用户封禁后**：前端 SplashScreen 的 `getMe()` 调用应该检查 `UserStatus`，封禁用户返回错误
4. **清空个人信息**：将 `Nickname`、`Avatar`、`Signature` 设为空字符串，`Gender` 设为 `Other`
5. **种子管理员**：在 `Program.cs` 的 `app startup` 中检查，如无管理员则自动创建
